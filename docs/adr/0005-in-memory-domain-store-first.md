# ADR 0005 — The domain store is in memory before it is in Postgres

- Status: accepted
- Date: 2026-08-25

## Context

The architecture places orders, customers, shipments and the policy index in
Postgres with pgvector. Phase 1 needed a working tool plane: five MCP servers over
a realistic dataset, with tests.

Two things pulled against starting with Postgres.

The dataset is generated, not authored. It is a pure function of a seed, it builds
in about a tenth of a second, and it fits comfortably in memory. Putting it behind
a database adds a schema, migrations and a container to every test run, and buys
nothing that a dictionary does not already provide at this size.

More decisively: a database-backed store written now would be a store nobody could
run. The tool plane has to be executable by anyone who clones the repository - that
is the whole premise of the curriculum - and a hard Postgres dependency at Phase 1
puts a container between a reader and the first lab.

## Decision

`backstop_domain.store.DomainStore` is a Protocol. `MemoryStore` implements it,
indexed on construction from a generated dataset. The MCP servers depend on the
Protocol, never on an implementation.

`PostgresStore` arrives in Phase 2, alongside the LangGraph checkpointer that makes
the database mandatory anyway. The schemas and extensions are already created by
`infra/sql/01-extensions.sql`, so that change is additive.

## Consequences

- Every test, lab and the end-to-end demo run with nothing started.
- The seam is explicit and typed, so the Postgres implementation is a new class
  rather than an edit to the servers.
- Pagination and page-size caps live in the store, so they are enforced identically
  by both implementations rather than being an accident of SQL.
- Cost: `MemoryStore` has no concurrency story and no persistence. Neither matters
  for read-only synthetic data, and the payments ledger - the only mutable state in
  the tool plane - is deliberately in-process too, so a restart is a clean slate.
- Risk: the Postgres implementation could drift from the Protocol. Mitigated by
  writing the store tests against the Protocol, so both implementations run the
  same suite.

## Alternatives considered

- **Postgres from the start.** Truest to the target architecture, and it would have
  made Phase 1 unrunnable for anyone without Docker. Rejected.
- **SQLite locally, Postgres in deployment.** Two SQL dialects to keep aligned, and
  no pgvector, so the retrieval path would have differed between environments -
  which is precisely where a difference does the most damage. Rejected.
- **Load fixtures from JSON files instead of generating.** Files would have to be
  committed, reviewed and regenerated by hand whenever the shape changed. The
  generator is smaller than the data it produces, and it can be parameterised for
  a smaller dataset in tests. Rejected.
